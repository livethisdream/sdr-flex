# ADR-0032: A GNU Radio flowgraph is a program, so it is an adapter

**Status:** Accepted — extends [ADR-0013](0013-external-decoders-as-subprocesses.md)

## Decision

**A GNU Radio out-of-tree module is reached the same way every other external decoder is:
as a subprocess, samples in on stdin, records out on stdout.** The flowgraph is a Python
script that ships with the tool in `server/flowgraphs/`, and the adapter row names it.

That needed exactly one new idea. For every other adapter, "is it installed" is a name on
PATH. For a flowgraph it is not: the command is an interpreter, which is always there,
and what actually has to exist is a **module inside it**. So an adapter may declare
`module`, and `available()` answers by asking the interpreter to import it. Without that,
the palette would offer a decoder that cannot run — the same failure as naming
`dump1090` on a box that has `dump1090-mutability`, arrived at from the other side.

Three smaller things follow:

- **The interpreter is a candidate list, like a binary is.** GNU Radio builds its bindings
  against one CPython; a box can have five. On the machine this was written on, GNU
  Radio's bindings are for 3.12 and `python3` is 3.11, so `python3 flowgraph.py` fails
  with `ModuleNotFoundError` and `python3.12 flowgraph.py` works.
- **`wants` may be a function of the parameters.** Almost every decoder takes one format
  at one rate. LoRa is sampled at a whole multiple of its bandwidth, so choosing 250 kHz
  bandwidth changes what the decoder must be fed — a static `wants` would have quietly
  starved every setting but the default.
- **The probe costs half a second and is cached** for the life of the process, paid at
  startup by `warm()` rather than on somebody's first click.

**The flowgraphs are written by hand, not exported from GNU Radio Companion.** A `.grc`
export carries a GUI, a throttle and a sample-rate variable that only make sense live.
What is wanted here is the receive chain and nothing else, ending in a print of one JSON
object per record — which the `jsonl` parser rtl_433 already uses reads unchanged.

## Why

**Why this matters more than one more decoder.** The standalone-CLI decoders are a finite
set: rtl_433, multimon-ng, dump1090, direwolf, minimodem, and a short tail. Everything
else modern in this field is a GNU Radio out-of-tree module — LoRa, M17, TEMPEST,
satellite telemetry, most of what a CTF is built out of. Without this they are all
unreachable; with it each one is a table row and a twenty-line script.

**Why not link GNU Radio in.** For the same reason nothing else is linked in (ADR-0013,
ADR-0015). The pipe is an interface these programs already have, a flowgraph that
segfaults kills a pipe rather than a session, and a GPL module invoked at arm's length is
aggregation rather than linking. It also keeps the zero-dependency rule intact: the tool
is still plain ES modules and Node's own libraries, and GNU Radio is something the
operator installed, like rtl_433.

**Why the LoRa fixture is generated by gr-lora_sdr's own transmitter**, when ADR-0025 says
every fixture is synthesized from a seed. A LoRa frame is chirp spread spectrum wrapped
in whitening, Hamming coding, interleaving, a Gray map, a header and a CRC. Writing all
of that in JavaScript to test somebody else's LoRa decoder would mostly be testing *our
reimplementation* of LoRa — and a reimplementation wrong in the same way as the decoder
would make the test pass and mean nothing. Using the decoder's own encoder makes the
check two-sided instead. Everything ADR-0025 actually asks for still holds: nobody
transmitted it, it carries its license and provenance, there is no noise or channel model
so it regenerates byte-identically (checked, not assumed), and it is 176 kB. The control
that makes it a decode rather than a decoder willing to find something anywhere is in the
suite: the same capture read at SF9 returns nothing.

## What this cost, measured

- GNU Radio 3.10.9.2 installs from the Ubuntu archive. No source build.
- `gr-lora_sdr` clones, builds and installs in about four minutes, first try.
- `gr-tempest` also builds clean, but is **not a fire-and-forget decoder**: its examples
  expose five to seven live operator knobs — `harmonic`, `epsilon_channel`,
  `horizontal_offset`, `lines_offset`, `inverted` — that a person turns until the picture
  locks, and two of its blocks (`normalize_flow`, `fine_sampling_synchronization`) return
  ±1e34 and NaN on short or clean inputs. It fits this adapter shape only if those knobs
  become adapter parameters, which the parameter strip can already draw. Not done here.
- A flowgraph reading 200k samples off the pipe: 0.18 s, no X11, no temp file.
- LoRa over the fixture through the adapter: 9 frames in 240 ms.

## Consequences

- `Identify` gains LoRa for free and ranks it first on the fixture, in 874 ms.
- An adapter row can now be a program, a program under any of several names, or a
  flowgraph inside an interpreter — and the report says which of those is missing.
- The container images do not carry GNU Radio. It is roughly a gigabyte, and the tool
  reports the decoder as not installed and names the module, which is the same thing it
  does for every other decoder somebody has not installed.
