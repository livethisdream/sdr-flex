# Direct-sequence spread spectrum, 127-chip m-sequence

BPSK spread by a 127-chip maximal-length sequence at 60 kchip/s, one code period per
bit, four samples per chip. 240 kS/s complex on 915 MHz. The polynomial is
`x^7 + x^4 + 1`, which is the one nearly everybody reaches for at that length.

21 dB of processing gain, which is what makes it spread spectrum and what makes it
unreadable until the code is known. Finding the code is the thing somebody analyzing a
direct-sequence signal is after; everything else follows from it.

**It carries a 900 Hz carrier offset on purpose.** A receiver that only works at exactly
zero offset passes every test written for it and no capture off the air, and a
despreader is worse than most in this respect: correlating across a whole code period is
a coherent integration across it, and 900 Hz at 60 kchip/s is two full rotations over
127 chips. The right code then scores no better than the wrong ones and the search
reports — quite correctly, and quite uselessly — that this is not a code it knows. So
the offset is measured first, by squaring, and divided out before anything is correlated.

**Nothing in the capture says which code it is.** The chip rate comes from the
transitions, the offset from the squared signal, and the code from a correlation search
over the standard families — every primitive polynomial up to degree 11, the Gold sets
built from the short ones, and the Barker words. Five hundred and fifty-seven codes, in
about a second.

The payload carries the same `aa aa 2d d4` preamble as the Manchester fixture, so the
sync-word path has something to find and a reader can see the byte alignment was right
rather than take it on trust. There is no CRC, and the framer says so.

**Nobody transmitted this.** Generated by `fixtures/make.mjs` from a fixed seed; it
regenerates byte for byte.
